## 0. 如何使用本档案

### 0.1 跨聊天使用方法
将本 `.md` 文件下载后，上传到 ChatGPT 的「小牵」Project 项目文件/项目知识中。之后在同一个 Project 的新聊天里，可以要求 ChatGPT 先读取本档案，再继续工作。

**不要只依赖聊天记忆。** 项目文件是完整资料基准；模型记忆只用于辅助理解，不能替代文档。项目文件可在同一 Project 的其他聊天中作为背景资料查阅，但新聊天仍应明确要求先读取本档案。

### 0.2 状态标记

| 标记 | 含义 | 使用规则 |
|---|---|---|
| **已确认/锁定** | 用户明确认可的需求、交互或视觉方案 | 后续不得擅自更改；修改必须先取得用户明确授权 |
| **功能已确认，视觉待核** | 功能规则已确定，但最终截图/全链路尚未逐项核验 | 可以写入需求，不可声称视觉已定稿 |
| **待核实/待补图** | 当前资料无法确认最终设计或完整行为 | 保留问题，不要猜测 |
| **待技术验证** | 设计意图明确，但平台接口、授权、数据或接入方式未知 | 原型可模拟，不能宣称真实能力已接通 |
| **假设/待验证** | 来自个人观察或推导，尚无足够样本证明普遍性 | 不得包装成市场事实 |
| **V2/长期方向** | 用户认可的未来探索方向，不属于当前 V1.1 原型范围 | 不要擅自加入 V1.1 |
| **已取消/被替代** | 旧方案已被后续决定取代 | 不得从旧 PRD 或旧原型中恢复 |

### 0.3 决策优先级
遇到文件、截图、历史聊天之间的冲突，按以下顺序处理：
1. 用户在最新聊天中明确确认的决定；
2. 本档案中记录的最新确认规则；
3. 最新《产品需求与交互设计基线记录》；
4. 用户明确认可并锁定的最终界面原图；
5. 较早版本 PRD、SRS、页面清单和原型，仅作历史参考。

**视觉原图是已确认页面的视觉基线，最新交互规则是行为基线。** 如果两者冲突，标记冲突并询问用户，不得擅自以“美化”或“统一设计”为理由改图。

# 第一部分｜项目概况

## 1. 项目定位
小牵是一项嵌入抖音原生体验的旅行行程功能，覆盖旅行内容发现、公开行程查看、私人行程规划、行前准备、旅行记录、内容整理和作品发布。

小牵**不是独立旅行 App**，也不打算重新开发抖音已经具备的搜索、收藏、个人主页、作品发布、图片美化、团购、支付、订单等原生能力。

核心设想：

> 用户在抖音刷到旅行内容后，可以直接查看博主的结构化行程；有需要时复制路线成为自己的私人行程，修改地点和交通、准备出行；旅行时按地点记录照片和体验；旅行结束后，将自己的路线与自己选择公开的旅行记录整理成抖音作品。

小牵同时服务两种内容价值：
- **行程规划价值：** 帮助用户把分散在多个平台的地点、路线、交通、价格、体验和商业信息组织起来。
- **内容分享价值：** 帮助普通旅行者按地点整理照片和体验，降低分享成本；也让旅行创作者发布更有结构的路线攻略。

## 2. 项目目标与当前交付目标

### 2.1 产品目标
减少旅行规划中跨平台搜索、反复切换、手工抄录、路线整理和后续内容整理的负担；让抖音旅行内容从“看视频获得灵感”进一步延伸为“查看可用路线、按需复制规划、记录真实体验和分享”。

### 2.2 当前项目交付目标
用户当前不是要把小牵完整开发上线，而是：
- 完成一套较严谨的产品需求与交互设计；
- 整理 PRD、需求分析、SRS、功能清单、页面/弹窗清单、流程与验收要求；
- 基于已经确认的界面原图制作一版**高保真、可点击、可交互、可演示**的原型；
- 用该项目作为互联网产品助理/初级产品经理求职作品集的重要案例；
- 让朋友能够体验并给出反馈。

原型的目的是展示和验证产品逻辑，不是完整产品开发。可使用模拟数据和本地状态，不要求接通真实抖音账号、地图、支付、团购或服务端接口。

## 3. 求职背景与作品集目标
- 目标岗位：互联网产品助理 / 初级产品经理。
- 用户缺少相关工作经验，学历条件也不是优势，希望通过一个相对完整、严谨的项目展示产品能力。
- 作品集重点应体现：真实问题发现、用户访谈、需求分析、竞品观察、产品定位、V1 范围取舍、PRD、SRS、流程图、页面与弹窗清单、原型、测试验收、迭代复盘。
- 不应把项目包装成真实上线产品，不得虚构用户规模、商业收入、平台授权或真实业务数据。
- 作品集需要清楚区分：用户亲身经历、访谈观察、产品推导、市场假设、技术待验证事项。

# 第二部分｜用户研究与需求分析

## 4. 用户亲身经历与问题来源
用户真实体验过多种旅行规划方式，主要信息来源包括：

| 任务 | 主要使用来源 |
|---|---|
| 旅行攻略记录 | 备忘录、纸质记录、十六番 |
| 目的地与景点灵感 | 抖音、小红书 |
| 景点项目、门票、预约、体验 | 抖音搜索、美团、大众点评、携程 |
| 美食推荐 | 抖音、小红书、美团 |
| 团购购买 | 抖音、美团 |
| 景点间路线 | 百度地图、高德地图 |
| 酒店住宿 | 美团、携程等平台，反复比较位置、价格和环境 |

### 4.1 真实痛点
1. **信息分散：** 景点、美食、交通、住宿、价格、门票、预约和团购分散在不同平台。
2. **重复搜索：** 看完博主视频后，需要逐个搜索景点和餐厅，再去其他平台找详情、价格和团购。
3. **记录容易遗漏：** 备忘录和纸质攻略格式不统一，容易漏记，不便携带和查看。
4. **收藏内容杂乱：** 抖音收藏很方便，但收藏多、内容杂时，用户需要再翻找；用户本人并不习惯为每类内容提前建立收藏夹。
5. **多博主信息难汇总：** 景点攻略和美食攻略经常来自不同博主，用户需要反复切换视频，手动整理。
6. **路线与预算冲突：** 景点、美食可能不顺路；价格可能超预算；天气变化也可能导致调整。
7. **交通比较麻烦：** 需要在地图软件中逐段搜索交通方式、距离、耗时和费用。
8. **旅行开销难记：** 多人出游时如果没记录价格，容易产生费用分摊争议；对习惯理账的用户尤其困扰。
9. **住宿决策繁琐：** 需要反复比较酒店位置、价格和环境。
10. **直接收藏博主攻略有局限：** 不能按个人喜好删掉不想去的点位，也不方便组合多个博主的地点。
11. **旅行记录与分享有门槛：** 用户愿意分享给朋友；如果照片整理和发布足够方便，也愿意发抖音作品，但不一定愿意从零写长篇攻略。

## 5. 用户真实规划过程
用户描述的典型流程：
1. 根据假期长短，先决定大致旅行范围：长假可选远一些的城市，短假选择附近城市。
2. 搜索周边或目标城市旅游推荐。
3. 把感兴趣的视频分享给家人或朋友，共同讨论并确定城市。
4. 搜索目标城市景点推荐，先形成候选地点。
5. 搜索目标城市美食推荐；美食和景点常来自不同博主。
6. 将距离较近的景点尽量安排在一起。
7. 根据行程天数和预算删减景点。
8. 进一步核对项目、价格、预约、体验、口碑、是否值得去。
9. 处理景点和美食不顺路、预算不合适、天气变化等问题。
10. 使用地图软件逐段比较出行方式。
11. 研究酒店位置、价格和环境。
12. 形成一份可在旅行当天反复查看的攻略。

如果不想做复杂攻略，用户也至少会搜索推荐城市、景点和当地美食，并可能购买团购。

## 6. 目标用户与使用方式
以下是当前基于个人经历和访谈推导的用户类型，不代表已经完成大样本验证。

### 6.1 详细规划型旅行者
- 会提前搜集大量景点、美食、交通、预算和住宿信息。
- 希望复制多个博主的地点，再自行筛选、增删和调整。
- 关注价格、项目内容、预约、真实评价和路线是否合理。
- 希望交通方案显示距离、预计时间和费用，但理解估算不一定准确。
- 需要在不同交通方式之间权衡省钱、省事和体验。
- 可能需要行前准备清单。

### 6.2 轻量参考型旅行者
- 不一定创建自己的私人行程。
- 可以收藏公开攻略，旅行时直接打开参考。
- 也可能复制行程，但不一定修改或发布作品。
- 不应强制所有用户点击“跟着玩”、复制行程或创建私人行程。

### 6.3 旅行攻略创作者
- 生产结构化、可参考的旅行路线。
- 关注路线、地点、交通、项目、价格、推荐理由、实拍和真实体验。
- 希望作品被浏览、收藏、复制，扩大内容影响力。
- 旅行结束后可能整理路线和内容，再发布完整攻略。

### 6.4 普通旅行分享者/体验分享者
- 不一定想成为专业攻略博主。
- 可能只想分享餐馆打卡照、景点照片、旅行氛围和简单感受。
- 更关注照片是否好看、音乐是否合适、模板是否有趣。
- 不应该被要求写专业点评或详细攻略。
- 需要低门槛地按地点整理照片并发布单地点测评或轻量作品。

## 7. 家人旅行与朋友旅行的差异

### 家人旅行
- 家人可能共同提出想去的景点。
- 用户通常承担后续具体规划：筛选景点、美食、路线、时间、地点和住宿。
- 其他家庭成员可能提供意见，但不一定参与详细安排。

### 朋友旅行
- 用户和朋友可能共同找景点、规划路线、比较餐馆。
- 也存在一个人负责规划、另一个人跟随的组合。
- 不同朋友之间的协作习惯差异很大。

### V1.1 取舍
用户接受 V1.1 暂时不支持多人实时共同编辑。朋友可以通过聊天提供建议，由行程创建者自行修改。多人权限协作进入 V2 候选。

## 8. 内容可信度与攻略质量
用户认为以下内容会共同提高信任：
- 实拍视频或照片；
- 详细、实用的信息；
- 项目和游玩方式；
- 价格；
- 真实游客评价或评论；
- 博主解释价格较高的原因；
- 团购或门票链接能帮助核实实际价格。

重要原则：
- 不能只有炫耀照片、缺乏实用信息；
- 也不能只有空泛口播、缺乏真实体验；
- 但 V1 不应强制每个地点填写专业评价；
- 允许不同详细程度的行程作品存在。

# 第三部分｜产品核心概念与版本范围

## 9. 行程与攻略的区别

| 概念 | 含义 |
|---|---|
| 私人行程 | 用户自己的路线和规划，可编辑、可保存草稿 |
| 公开行程作品 | 用户将自己的路线和选择公开的内容发布到抖音 |
| 完整行程攻略 | 公开路线加上用户选择公开的照片、旅行记录、体验、商业链接等；但可以只发布路线，不强制有评价 |
| 单地点测评 | 只分享一个地点的本人照片、体验和相关内容，不需要公开整段行程 |
| 旅行记录 | 私人行程中的通用记录，可关联地点，也可不关联地点；可包含文字、照片和多个商业链接 |
| 跟玩/复制行程 | 将当前公开作品中的路线结构复制为用户自己的可编辑私人行程，不复制原作者原创素材 |

**最新发布规则：** 用户允许发布仅包含路线、地点、交通安排，并搭配封面、文案或音乐的作品。不能强制至少一条旅行记录、照片、评价或商业链接。

## 10. 核心产品价值
1. 在抖音发现旅行攻略后，直接查看结构化路线。
2. 不创建私人行程也可以收藏或直接参考公开攻略。
3. 需要规划时，可复制公开路线形成自己的私人行程。
4. 在同一份行程里组织地点、时间、路线和交通。
5. 按地点记录照片和体验，不要求旅行当场完成。
6. 旅行结束后从自己的记录中选择内容，降低作品整理成本。
7. 通过抖音原生地点、团购、门票等能力承接商业服务（实际接入待验证）。

## 11. V1.1 当前范围

### 核心功能
- 抖音推荐页中的行程作品展示；
- 行程频道；
- 公开完整行程详情；
- 公开行程收藏、直接查看和可选复制；
- 私人行程创建与编辑；
- 地点搜索与加入；
- 地点编辑、交通方式设置、路线预览；
- 地点拖拽排序、增加和删除；
- 行程草稿与编辑草稿；
- 私人行程管理；
- 行程状态：待出发、进行中、已完成；
- 行前准备轻量清单；
- 旅行记录（地点关联/整体记录、多图批量上传、隐私）；
- 完整行程攻略发布；
- 单地点测评发布；
- 发布前二次确认、发布失败保留草稿；
- 抖音个人主页“我的行程”入口；
- 抖音原生地点详情、团购、门票等页面的跳转占位；
- 原生页面返回后恢复原行程上下文。

### 明确不要求 V1.1 实现
- 真实抖音账号授权和真实服务端；
- 真实地图路线 API、实时交通、实时价格；
- 真实团购支付、退款、订单、核销；
- 真实抖音作品发布接口；
- 真实达人佣金结算；
- 完整商业数据后台；
- 完整多人实时协作；
- 独立旅行 App。

## 12. V2 / 长期探索方向

### 12.1 多人协作
- 邀请成员加入共享行程；
- 管理员、编辑者、只读查看者；
- 邀请时选择权限；
- 管理员调整成员权限；
- 多人同时编辑冲突处理；
- 朋友自由行和旅行社小团场景。

用户希望有权限控制，避免所有成员随意修改公共行程；V1 已接受暂不支持。

### 12.2 旅行作品模板生态
- 官方推出旅行作品模板；
- 用户按地点整理照片后，系统辅助生成更美观的旅行作品；
- 创作者投稿模板；
- 官方创作者大赛和模板激励；
- 探索打卡姿势、热门地点拍照模板、主题合集。

V1 先支持按地点批量上传照片，并优先复用抖音现有图片编辑和配乐能力。醒图、可颂等字节系产品的具体跨产品接入能力待验证。

### 12.3 旅行社与地陪
- 旅行社发布结构化小团行程；
- 用户查看、报名、购买；
- 导游管理团队行程和游客；
- 景点打卡、集合和到场管理；
- 地陪发布服务路线、接单和联系。

以上为长期商业化畅想，不进入当前 V1.1。

### 12.4 创作者商业生态
- 头部创作者曝光合作；
- 中小创作者通过团购等商业内容获得收益；
- 创作者收益看板、商业合作管理等能力；
- 需要平台权限、商业规则和数据归因验证。

## 13. 当前页面基线

> 页面编号沿用历史讨论标识，不擅自重编号。编号不代表每个页面都必须独立开发。

| 编号/名称 | 当前状态 | 核心内容与规则 |

- 继续编辑；
- 保存草稿并退出；
- 放弃修改。

## 21. 单地点测评发布

- 单地点测评：只分享一个地点的本人体验、照片、商业链接等，不必公开整个行程。

V1 方向：
- 复用用户自己的地点记录、照片和体验；
- 不强制公开整段路线；
- 不要求专业长篇点评；
- 可使用抖音原生作品发布能力；
- 完整页面视觉和交互链路仍待核查。


## 22. 我的行程管理页
### 入口
- P02 行程频道搜索框右侧“我的行程”；
- 抖音原生“我”个人主页功能入口“我的行程”；
- 两个入口通向同一个管理页。

### 管理页
顶部五种状态分类：
- 全部；
- 待出发；
- 进行中；
- 已完成；
- 草稿。

右上角“＋新建行程”。

下方纵向封面卡片，展示标题、目的地、日期、天数、地点数、状态；根据状态显示编辑/查看、继续记录、发布作品、继续编辑等操作；更多操作收进菜单。

这里的“草稿”只指尚未完成编辑的私人行程规划草稿，不是编辑草稿、旅行记录草稿或作品发布草稿。

### 删除
- 删除私人行程不可逆；
- 必须二次确认；
- 删除私人行程不自动删除已发布公开作品。

## 23. 抖音原生“我”个人主页
已确认视觉方向：
- 使用虚构旅行用户头像、昵称、背景和账号信息；
- 不使用用户本人真实资料；
- 功能入口压缩为单排六个；
- 六个入口包含“我的行程”；
- “我的行程”进入统一私人行程管理页；
- 个人主页“作品”网格复用抖音原生作品展示；
- 原生“草稿箱”固定排在网格第一个位置，只表示作品发布草稿；
- 完整行程作品封面右上角使用低调小尺寸半透明“行程攻略”标识；
- 单地点测评可标“地点测评”；
- 不建立独立“我的作品”管理页；
- 保留原生作品展示结构和底部导航。

## 24. 复制公开行程规则
用户可选择：
- 只收藏公开作品；
- 直接查看和参考公开行程；
- 需要规划时，选择复制为自己的私人行程。

复制不是查看或使用公开攻略的前置条件。

复制范围：
- 地点；
- 地点顺序；
- 日程结构；
- 可用的交通参考等路线规划信息。

明确禁止自动复制：
- 原博主照片；
- 原博主评价/体验；
- 原博主推荐文案；
- 原博主原创内容；
- 原博主商业推广链接并将其变成用户自己的推广内容。

复制后私人行程由用户自由编辑。首次复制可在内部统计来源作品/博主，用于统计复制行为；不要求私人行程长期展示原作者标识。用户发布新作品时使用自己的照片、体验和主动选择的内容。用户可以自行在抖音文案中 @ 原博主，但不强制。

## 25. 原生地点、团购、门票、订单和异常
- 不独立开发 P06 地点详情。
- 地点详情、景点百科、餐厅、团购、门票、购买、支付、退款、订单、核销等复用抖音原生能力。
- 小牵不自动同步订单、支付金额或核销状态。
- 不新增订单管理页面。
- P05 对应地点保留清晰可点击的地点详情、团购、门票入口。
- 原型中可使用可替换的原生页面截图占位节点。
- 从原生页面返回，恢复原日期、地点、滚动位置。
- 未保存编辑内容也要保留。
- 商品下架、链接失效、网络异常导致无法打开时，显示轻量提示：“当前内容暂时无法打开，请稍后重试”。
- 停留原行程页面，不新建独立错误页面。

## 26. 防重复提交
以下关键操作必须防重复：
- 完成编辑；
- 直接加入待出发（如对应入口存在）；
- 确认发布。

首次点击后进入加载状态并禁用重复点击；成功只创建一份；失败保留内容并允许重试；超时先核实操作结果，避免重复创建。

# 第六部分｜数据对象与草稿边界

## 27. 核心数据对象
建议原型和需求文档至少区分以下对象：
1. **私人行程**：用户拥有和编辑的路线、日期、地点、交通等。
2. **公开行程作品**：由私人行程整理发布，发布后为独立快照。
3. **公开作品路线副本/复制来源记录**：用户首次复制公开作品时产生的内部来源统计信息。
4. **地点**：包含名称、类型、地址/坐标、计划到达时间、停留时间、预计花销等。
5. **交通路段**：起点、终点、交通方式、估算距离、估算耗时、可选费用。
6. **旅行记录**：可关联地点或不关联地点；含照片、文字、商业链接、可见范围。
7. **旅行记录草稿**：归属私人行程。
8. **私人行程规划草稿**：尚未完成的新行程。
9. **已有行程编辑草稿**：依附已有私人行程，与正式版本并存。
10. **作品发布草稿**：复用抖音原生作品草稿箱。
11. **原生商业资源引用**：地点详情、团购、门票、商品、直播等跳转信息。

## 28. 四种草稿必须严格隔离

| 草稿类型 | 存放位置/归属 | 说明 |
|---|---|---|
| 新建私人行程规划草稿 | 我的行程管理页“草稿” | 还未完成创建的私人行程 |
| 已有私人行程编辑草稿 | 依附原私人行程 | 不单独生成行程卡片，与正式版本并存 |
| 旅行记录草稿 | 对应私人行程的旅行记录 | 保存未完成的文字/照片/链接记录 |
| 作品发布草稿 | 抖音原生作品草稿箱 | 与私人行程和旅行记录草稿分离 |

## 29. 已有行程编辑草稿详细规则

### 场景 A：从正式行程 A 开始编辑
如果没有旧编辑草稿：
- 保存到原行程：保存当前进度到正式版本；
- 另存为编辑草稿：保存为依附原行程的编辑草稿；
- 取消：关闭选择，不丢当前编辑内容。

如果已有旧编辑草稿 B：
- 选择“另存为编辑草稿”前提示旧草稿将被覆盖；
- 用户选择“覆盖旧草稿”才覆盖；
- 选择取消，不覆盖旧草稿，保留当前正在编辑的修改。

### 场景 B：从已有编辑草稿 B 继续编辑得到 B2
- “保存到原行程”：将 B2 保存为正式版本，返回原私人行程详情；原草稿 B 仍保留原始内容，不自动同步或覆盖。
- “另存为编辑草稿”：以 B2 更新当前草稿 B；保存成功后返回原私人行程详情，展示正式版本，而不是刚保存的编辑草稿。
- “取消”：关闭保存方式选择，保留当前编辑内容。

### 重新打开行程
- 从“我的行程”重新打开存在编辑草稿的私人行程时，轻量提示“发现未完成的行程编辑”，提供“继续编辑草稿／查看原行程”。
- 继续编辑：恢复草稿的地点顺序、时间、交通方式和其他内容。
- 查看原行程：进入正式保存版本，默认“行程安排”，不删除草稿。
- 在正式详情点击“编辑行程”且存在编辑草稿时，弹出“继续编辑草稿／编辑当前正式行程”。
- 两种选择都不立即删除或覆盖旧草稿。
- 草稿与正式版本不一致时，恢复草稿原内容，不增加自动合并或额外差异弹窗。
- 只有点击“完成编辑”并成功保存，才按既定规则清除已使用的编辑草稿。

# 第七部分｜增长、创作者与商业化思路

## 30. 创作者类型和价值诉求

| 创作者类型 | 可能关注的指标/收益 | 主要内容形式 |
|---|---|---|
| 头部旅行博主 | 浏览量、收藏量、行程复制量、粉丝影响力 | 自然展示旅行内容和小牵行程功能 |
| 中小型/本地旅行博主 | 团购、门票等商品成交和佣金机会 | 本地景点、美食、体验、团购推荐 |
| 功能教学/创作者运营博主 | 教程内容流量、创作者教育价值 | 教如何使用新功能、创作和经营内容 |
| 普通旅行用户 | 分享自己的照片、体验和旅程 | 轻量照片分享或完整行程作品 |

这些是用户提出的运营观察和策略假设，需验证，不代表所有创作者都符合该模式。

## 31. 冷启动策略假设
用户倾向第一笔推广预算优先追求功能曝光，投向流量较大的旅行博主。

### 第一阶段：头部创作者建立认知
- 通过创作者激励、官方活动、付费达人合作等方式；
- 邀请头部旅行博主在正常旅行作品中自然展示和使用小牵；
- 不要求旅行博主统一制作功能教学视频；
- 让粉丝看到真实旅行内容和可查看的行程结构。

### 第二阶段：中小创作者自发参与
- 当中小型、本地旅行博主知道该功能后，可能因内容曝光和团购佣金机会主动使用；
- 通过本地景点、美食、门票、团购等内容形成更丰富的行程作品供给。

### 教学内容的角色
功能教学博主和旅行博主不是同一种内容创作者。教学博主可以讲解新功能、如何创建行程、如何发布、创作者运营等；旅行博主则以真实旅行内容为主，自然展示功能。

### 需要验证的假设
- 头部达人内容能否有效带来新功能认知；
- 粉丝是否会查看、收藏、复制行程；
- 中小创作者是否愿意自发使用；
- 行程作品是否有助于团购/门票转化；
- 佣金和流量是否足以形成持续创作动力；
- 头部和中小创作者的指标偏好是否确实不同。

不得编造达人收入、粉丝增长、平台流量成绩或佣金资格。用户曾提到“约 5000 粉丝可开通某类商单功能”，这属于待核实信息，不得直接写为确定平台规则。

## 32. 可能的增长指标

### 内容发现与使用
- 行程作品曝光量；
- 完整行程详情打开率；
- 收藏率；
- 行程复制率；
- 行程详情停留和关键模块点击情况。

### 创作者
- 发布行程作品的创作者数；
- 头部/中小/本地创作者参与情况；
- 创作者持续发布率；
- 行程作品质量与用户反馈。

### 商业转化
- 团购/门票链接点击；
- 商品详情到达；
- 购买转化（需平台数据与归因支持）；
- 创作者佣金（需商业平台规则支持）。

### 内容分享
- 旅行记录创建率；
- 多图记录使用率；
- 单地点测评发布量；
- 完整行程攻略发布量。

注意：浏览、收藏、复制、实际出行、购买是不同层次的行为，不能混为一谈。行程复制不等于真实出行或消费。

# 第八部分｜设计原则、待验证事项与项目进度

## 33. 不要过度设计
- 不是每一个用户行为差异都需要新增功能。
- 用户旅行中临时改变计划，不需要强制修改攻略；想改就改，不想改就不改。
- 不强制用户实时打卡、修改行程或记录体验。
- 不强制所有人复制公开攻略。
- 不强制所有地点都写评价。
- 不强制发布作品包含旅行记录。
- 不为了“完整”增加非必要弹窗、提醒、确认步骤。
- 仅在确有风险或已确认需要时使用确认弹窗。
- 不要为了视觉统一而更改锁定组件。

## 34. 视觉与交互锁定原则
用户已明确提出长期要求：
- 所有逐页确认的视觉、结构、组件、顺序、尺寸、交互都是锁定基线。
- 增加功能或修改局部时，只改用户明确指定区域。
- 生成新效果图或原型前逐项核对已确认版本。
- 禁止擅自重画、替换或改变其他区域。
- 不确定时先查历史素材或标记待核实，不得猜测。
- 不得因新原型实现方便而改变原始设计逻辑。

## 35. 待核实事项与风险

### 35.1 产品与视觉待核实
- 所有历史截图中哪些是最终锁定版，哪些是旧版；
- P01、P02、P05、P07-B、P08、私人行程三状态、我的行程、个人主页等截图与页面映射；
- P07-B 原图与路线预览弹层的逐项一致性；
- 单地点测评完整发布链路是否已有最终截图；
- 复制公开行程的具体入口、完成后的落点和失败反馈；
- P02 搜索与原生搜索能力如何衔接；
- 原生地点详情、团购、门票占位节点需要替换哪些真实截图。

### 35.2 技术待验证
- 抖音内嵌频道/生活服务入口的实际开放能力；
- 原生地点、团购、门票、商品、直播深链；
- 作品发布和编辑权限；
- 抖音图片编辑、美颜、音乐等能力的可接入方式；
- 地图数据、路线、交通估算和定位服务；
- 作品复制来源统计能否获取；
- 商业商品链接、分佣、达人资格和归因规则；
- 隐私权限与朋友可见范围如何与抖音账号体系对齐。

### 35.3 研究假设待验证
- 多数年轻旅行用户的攻略分工模式；
- 头部旅行博主更看重曝光，地方中小博主更看重佣金；
- 头部达人曝光会带来中小创作者自发供给；
- 行程卡片可能提升旅行攻略的保存和使用价值；
- 按地点批量整理照片可能提升普通用户发布意愿；
- 模板可能提升旅行作品创作率；
- 用户复制行程是否能带来实际出行和商业转化。

# 第九部分｜原型制作与 Codex 交接

## 36. 原型定位
当前制作的是一套用于作品集展示和用户体验验证的高保真交互原型：
- 不是完整产品开发；
- 不要求真实抖音账号、服务端、支付和地图接口；
- 可以用本地状态和演示数据；
- 关键交互必须实际可点击、数据状态一致；
- 不允许只有静态页面或 PPT 式跳转。

## 37. Codex 应自动识别截图
用户不希望为一版阶段性原型花费大量时间手动整理截图。

给 Codex 的要求：
1. 用户可以批量上传未分类截图；
2. Codex 自行识别截图中的页面、状态、弹窗和组件；
3. 根据标题、导航、按钮、地图、时间轴、视觉结构等匹配页面；
4. 将截图与 PRD、SRS、页面清单和本档案进行映射；
5. 识别连续滚动截图，不把同一页面拆成多个独立页面；
6. 保留原始文件名；
7. 区分重复图、旧版图和已确认图；
8. 不确定的地方列为待确认，不得擅自选择；
9. 输出简短的《截图识别与页面映射清单》；
10. 用户不需要逐张命名、分类或填写说明。

用户明确说“截图已上传完毕，可以开始制作”之前，不要擅自开始最终视觉实现。

## 38. 原型技术与交互要求（供 Codex 参考）
可采用 React + TypeScript + Vite，优先检查已有项目后再实现。建议：
- 手机竖屏适配，参考 390×844；
- 桌面端以手机模拟器展示；
- 页面、弹窗、底部弹层、选项卡和按钮可实际操作；
- 状态管理统一；
- localStorage 等本地持久化可用于演示；
- 模拟地点搜索、路线、交通和商业链接，明确标注为演示数据；
- 原生页面用可替换占位节点；
- 返回时恢复来源页面、日期、地点和滚动位置；
- 不能实现的功能明确标记，不得假装已完成。

## 39. 核心验收路径
至少验证以下流程：
1. P01 推荐页 → 行程作品 → 阅读完整行程 → 返回原位置；
2. P01 → P02 行程频道 → 作品详情 → 返回频道原位置；
3. P02 → 我的行程管理页；
4. 抖音“+” → 选择行程 → P07-B；
5. 搜索芜湖八佰伴 → 加入行程 → 地点编辑；
6. 地点编辑 → 交通方式弹窗 → 确认 → 返回地点编辑并保留字段；
7. 编辑器交通栏 → 交通方式弹窗 → 返回编辑器；
8. 路线预览弹层打开/关闭，保留编辑状态；
9. 长按拖拽地点，地图和路段同步更新；
10. 删除有记录地点，确认后记录保留为不关联地点记录；
11. 保存新建私人行程草稿，重新进入后恢复；
12. 编辑已有行程，验证“保存到原行程/另存为编辑草稿/取消”；
13. 恢复编辑草稿或查看正式版本；
14. 完成编辑后进入私人行程详情；
15. 待出发、进行中、已完成三状态切换；
16. 待出发状态添加旅行记录；
17. 旅行记录一次批量上传多张照片；
18. 保存旅行记录草稿、退出和恢复；
19. P08 三屏内容选择、整理、发布设置；
20. 发布前二次确认；
21. 发布失败保留作品草稿；

# 补充核对｜容易在后续聊天中遗漏的具体决定

以下内容补充到主档案，尤其用于防止新聊天或原型开发时漏掉细节。

## A. 入口与原生能力
- P02 行程频道搜索框右侧必须有醒目的“我的行程”图标入口，图标在上、文字在下。
- 抖音原生“我”个人主页也有“我的行程”入口。两个入口共同通往同一个私人行程管理页，不是二选一。
- 个人主页功能入口为单排六个，包含：待收货/我的订单相关、观看历史、我的钱包、我的客服、我的行程、全部功能。具体图标和样式以已确认个人主页原图为准。
- 个人主页作品网格首位是抖音原生“草稿箱”，仅代表作品发布草稿；私人行程规划草稿在“我的行程”管理页的“草稿”分类中。
- 不建立独立“我的作品”管理页；公开完整行程攻略和单地点测评复用抖音原生作品展示，作品发布草稿复用抖音原生草稿箱。
- P01 行程作品入口使用此前已确认的直接“阅读完整行程”入口，不要改到视频文案或评论区。
- 用户可以仅收藏公开作品、直接查看并跟着参考，也可以在准备出行时再复制；复制和创建私人行程不是使用公开攻略的前提条件。
- “跟着玩/复制”如在原型中保留，必须是可选行为；不能强迫轻量用户点击或创建行程。

## B. 私人行程、作品与记录的关系
- 一条已完成私人行程可以多次发布完整行程攻略，也可以发布多个单地点测评；每次发布的作品彼此独立。
- 发布作品是从私人行程和用户自己选择公开的旅行记录中整理内容，不是把来源博主作品重新发布。
- 已发布作品是独立快照。后续修改私人行程不自动同步已发布作品。
- 删除私人行程不会删除已发布作品；删除作品也不会删除私人行程或其他作品。
- 已发布作品当前暂不支持修改；平台真实可修改能力需核实。
- 作品草稿不会自动同步来源私人行程后来新增的记录。再次打开作品草稿时，可以轻量提示有新增可选公开内容，由用户主动选择是否加入；原有编辑结果不变。
- 用户可以在待出发状态下记录、上传照片和商业链接；“开始行程”只改变行程状态，不是记录或发布的前置条件。
- 用户也可以从待出发直接标记为已完成，适用于旅行结束后补做攻略的情况。
- 一条旅行记录可添加多个团购、门票或其他相关链接；链接归属于该条记录，与文字和照片一起管理。

## C. 旅行记录与照片操作习惯
- 用户添加照片的时间不固定：游玩时有空可以随手上传；忙时可以晚上回酒店修图后集中上传；也可以整趟旅行结束后再补。
- 小牵不要求用户在景点现场完成上传，不要求每天按时打卡。
- 用户明确要求一次性多选多张照片归入同一条记录，不接受逐张上传、逐张写感受的繁琐流程。
- 一条记录可以只有多张照片，不强制专业文字评价；也可以给整组照片写一段体验。
- 普通分享者更关注照片是否好看、配乐是否合适、作品是否有趣；V1 不要强迫普通用户写专业测评。
- 未来模板生态属于 V2；V1 优先复用抖音现有图片美化、配乐和作品发布能力。实际跨产品接入方式待验证。

## D. 行程规划中的价格、交通与时间
- 用户重视价格和预算，但不同用户对省钱、省事和体验的权衡不同。
- 交通方式和费用可以作为估算参考，不应被描述为绝对准确。
- 博主如果标注较贵的项目，用户希望其解释贵的原因；如果没有标价，可以自行搜索、添加估算或通过相关团购链接核实。
- 交通方式不应强制推荐“最便宜”方案；观光车等交通可能提供更好体验，即使费用更高也可能值得。
- 用户到现场后可能临时改变交通选择，例如原本步行、后来觉得累而购买观光车票；不要求立即回到行程中修改。普通用户可按现场情况灵活游玩。
- 用户旅行中临时改变计划，不需要额外设计“自动重排行程”功能；想改就编辑，不想改就不改。
- 用户提到酒店筛选、天气变化、预约、预算等是真实规划痛点，但除 P07 已确认的地点/交通/时间/花销字段外，不代表 V1.1 已经确认酒店比价、天气提醒、自动预算或预约管理模块。不得自行增加这些复杂功能。

## E. 复制路线与原创内容边界
- 复制只用于取得路线规划结构，不能自动搬运原博主的照片、评价、体验、推荐文案或商业推广链接。
- 用户认为复制后就应直接使用自己的照片、评价和体验；不应把别人的作品换个账号再发一遍。
- 首次复制来源可用于内部统计，例如统计某博主的行程被复制次数；但不要求私人行程页面长期显示“来自某某博主”。
- 用户发布自己作品时可以自行在文案中 @ 原博主或添加话题，但不强制。
- @ 原作者是社交互动方式，不等于完整解决版权问题；仍需遵循平台版权和内容治理规则。

## F. 内容冷启动策略
- 用户认为第一笔冷启动预算应优先追求功能曝光，投入流量较大的旅行博主。
- 旅行博主应像平时一样发布精彩旅行内容，自然而然展示小牵的行程能力；不应要求旅行博主拍成“教你怎么用小牵”的教学视频。
- 功能教学博主与旅行博主是不同内容类型：教学博主可以讲解新功能、如何使用、创作者运营和商业机会。
- 头部旅行博主可能更关注浏览、收藏、复制行程等反馈；中小/本地带货博主可能更关注团购成交和佣金。这是用户的行业观察和增长假设，必须验证。
- 头部达人合作之后，期待中小型本地旅行博主因流量和商业机会主动参与，逐渐形成内容供给；该增长闭环尚未被数据验证。
- 商业合作需明确披露，不能编造收入、流量、粉丝增长或平台佣金资格。

## G. 原型与项目工作方式
- 用户希望把所有已确认界面截图直接批量交给 Codex，让 Codex 自己识别截图属于哪个页面、状态、弹窗和组件；用户不想花大量时间逐张重命名和分类。
- Codex 应自动输出截图识别与页面映射清单，保留原文件名，识别连续滚动截图和弹窗叠层，无法判断的项目标记待确认。
- 用户可以接受这只是阶段性演示原型，不是最终上线产品；但必须是真正可点击、可交互、能演示核心数据和返回逻辑的高保真原型。
- 用户对此前生成的原型评价很差，指出大量交互有问题。因此新原型必须以最新需求和锁定截图为依据，不能把旧原型作为正确答案。
- 现阶段目标是先有一份可分享给朋友、可体验的原型，再基于体验验收和迭代；不是为了一个尚未最终定稿的原型耗费大量人工做图片分类。
